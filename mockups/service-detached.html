Service Definition → Detached

One new checkbox on the service form, next to Interactive Shell Env. When it is on, the command is started in its own session, so quitting ai-critic, restarting it via keep-alive request restart, or an ai-critic crash leaves the process running. An explicit Stop still stops it; a new ai-critic instance adopts the survivor and shows it as running instead of starting a second copy.

Lifetime deliberately does not take effect immediately — same as enable/disable, which never starts or stops a running service. Saving the form only writes the definition; a running process keeps the lifetime it was started with, the card shows an amber restart to apply marker, and the user restarts manually when convenient.

Defaults Detached = off (existing services unchanged, omitempty in JSON) Applies at next start only — never auto-restarts Reminder form notice + card chip + save toast Data services.json → detached → API (detached, detachedActive) → UI

4 · Saved value vs running process — what the UI showsstate matrix

detached attached detached + restart to apply “Running as attached. Saving only updates the definition — restart to apply detached.”
attached detached restart to apply (no detached chip) “Running as detached. Restart to stop it from outliving ai-critic — until then it still survives quit.”
any stopped detached only if saved on none — the next start simply uses the saved value
Why a backend field: the chip must survive a page reload, and the definition no longer tells us how the current process was started (saving updates the definition, not the live session). So the status payload carries detached (saved) and detachedActive (how the live pid was started) — the UI compares the two and never guesses.
Row 4 is the one users underestimate: turning Detached off for a running process does not make it die on quit — only a restart does. Hence the explicit amber warning instead of a silent save.

Event Attached Detached
Quit ai-critic app / server SIGTERM → stopped Left running; own session survives parent exit
keep-alive request restart Stopped, autostarted by the new instance Never signalled; new instance adopts the pid
ai-critic crash Orphan is reclaimed/stopped at next boot Orphan is adopted at next boot, shown as running
Save the form (flag changed) Nothing happens to a running process — definition only; the card shows restart to apply
Explicit Stop / service stop Stops Stops — detached is about implicit exits only
Shutdown-time cleanup backstop Killed Skipped, so a slow cleanup cannot kill a survivor
Definition deleted while running Stopped by the supervisor (definition went away) Stopped too — an unowned process would be invisible
Public port / tunnel after quit Gone Local port stays; public URL returns when ai-critic runs again
Migration: no change for existing services — detached is omitempty and defaults to false, so the services JSON golden test stays byte-identical.

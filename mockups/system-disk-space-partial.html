System · Disk：把 partial 讲清楚 + 扫描预算提到 10 分钟

今天这个页面在真机上永远是 partial + time budget，脚注只有一行 ~/Library/Containers (read timed out) · ~/Library/Group Containers (read timed out) · /home (autofs mount)， 而头部同时写着 432 dirs skipped —— 这两个数字既不相等也不互相解释： 432 是 no_access_dirs（权限错误，完全没有记录路径）， 308 是 skipped（只有超时 + 挂载点两类）。 所以"为什么 partial"今天在数据层就是不可回答的，不是 UI 排版问题。
本稿做两件事：① 把 scanBudget 从 300 s 提到 600 s； ② 让 partial 变成一个可以点开、能列出"哪些目录没扫到、具体什么错误"的面板， 并且服务端按前缀归并（308 条原始记录 → 5 组），只保留最有意义的那些。

三个前提（请在 Decisions 里确认）
① partial 只表示"核心目录没走完"，不再兼职表示"有目录读不到"。后者是一个始终存在的独立事实（权限、超时、按设计跳过的挂载点），用独立的 N folders not counted 入口暴露；这样预算提到 10 分钟后 partial 有机会变成 core folders scanned， 而"还有 490 个目录读不到"仍然诚实地摆在那里。
② 无路径 = 不可解释：analysis_scan_queue.go:159 目前只 settle(..., noAccess=true, skipped=nil) 就完事，权限错误连路径都不留。 这轮必须把每一条都记成 SkippedPath{path, kind, reason}，否则 UI 再怎么排版都是空的。
③ 归并在服务端做，随报告一起落库（coverage.skip_groups），CLI / Web / 历史报告共用同一份口径；原始明细封顶保留，不随报告体积线性增长。
下面所有数字取自真机报告量级（20261114-203720：300 s、9.79M 文件、401 GB / 459.8 GB、priority 3/6、no_access 432、skipped 308），个别项做了示意。

建议 · 数据模型 / 归并算法 / 接口

1. 预算：300 s → 600 s

位置改动说明
analysis_manager.go:16const scanBudget = 10 * time.Minute唯一的预算开关。软截止：到点后 truncated=true，已完成的部分照常出报告。
analysis_scan_run.go:111scanGrace 保持 15 swalk 最多越界 15 s 收尾；意味着最坏墙钟 ≈ 615 s。
analysis_scan_run.go:11fallback 120 s 保持不动只有不传 Budget 的调用方（测试）走这个值。
dirReadTimeout保持 1 s约 306 个卡死目录 × 1 s ≈ 306 s，正好塞得进 600 s；不建议同时调大，否则它们会挤掉真正的扫描时间。

为什么 10 分钟够：上一轮 300 s 走了 401 GB 且 priority 只完成 3/6，其中约 306 s 花在 ~/Library/Containers 的 283 次 1 s 超时上（LIFO 深度优先让 ~ 一开始就独占队列）。600 s 把"超时开销"和"有效扫描"都算进去仍有富余。如果实测还差，再考虑把 ~ 从 priority roots 里拿掉、或给每个 root 加独立配额 —— 那是第二个问题，本稿不动。

2. 可解释性：先补数据，再谈 UI

今天只有 两处产生 SkippedPath：abandon()（"read timed out"）和 skipDir()（"autofs mount" / "cloud drive"）。权限错误在 analysis_scan_queue.go:159 直接 settle(..., noAccess=os.IsPermission(err), skipped=nil) —— 路径和原因全丢，只加了一个计数。所以 432 dirs skipped 在数据层就是不可解释的。这一步必须补：

type SkippedPath struct {
    Path   string `json:"path"`              // ~-relative, e.g. ~/Library/Mail/V10
    Kind   string `json:"kind"`              // permission | timeout | io | by_design
    Reason string `json:"reason"`            // 原样 errno 文本: "operation not permitted"
    Depth  int    `json:"depth,omitempty"`   // 便于归并
}

// 三类产出点统一走一个 helper:
//   permission/io  -> settle(..., skipped: &SkippedPath{Kind:"permission", Reason: err.Error()})
//   timeout        -> abandon(): Kind:"timeout", Reason:"operation timed out after 1s"
//   skipDir()      -> Kind:"by_design", Reason:"autofs mount" | "cloud drive"

Report / ReportSummary 增加 not_counted_total（口径统一 = 所有 kind 的条数），替换 UI 里那个跟 skipped 对不上的 no_access_dirs 展示。no_access_dirs 字段保留不动（CLI 和老报告还在用）。

3. 前缀归并算法（服务端，随报告落库）

步骤规则真机效果（308 条）
① 归一home 前缀 → ~；去掉末尾 /；Depth = 段数—
② 分桶key = (kind, prefix)，同 kind 才合并（同一目录既超时又权限的情况必须分两行，否则原因会撒谎）—
③ 取前缀home 下取前 3 段（~ / Library / Containers）；绝对路径取前 2 段（/private/var）；不足则用整条路径~/Library/Containers/com.x/Data → ~/Library/Containers

5. Decisions（请逐条拍板）

  1. 预算 600 s（+15 s grace），dirReadTimeout 保持 1 s —— 确认？
  2. partial 语义收窄为"核心目录未走完"，"有目录读不到"独立成 not counted 中性入口 —— 确认？（这决定了 10 分钟后 partial 会不会自然消失）
  3. 前缀深度：home 3 段 / 绝对 2 段。是否改成"动态取最长公共前缀"？（更准，但同样要写规则表，且报告 diff 不稳定）
  4. 单例不折叠（/home 保留全路径）—— 确认？
  5. 原因分四类 permission | timeout | io | by_design，界面用 errno 原文做副标题 —— 是否需要更细（如区分 EPERM / EACCES / ENOTDIR）？
  6. by_design 分组单独成色、排在最后，且 TCC 提示只在 permission 组 ≥ 20 个时出现 —— 确认？
  7. 组上限 8、卡片内展示 4，其余折成 N more groups (M dirs)，skipped_total 永不被截断 —— 确认？
  8. 原始明细封顶 200 条随报告存储（今天 308 条 ≈ 30 KB，10 分钟后可能翻几倍）—— 同意封顶还是全存？
  9. 老报告不迁移、不回填，历史里标 legacy —— 确认？
  10. 不做："每目录重试"、"用户手动排除某前缀"、"扫描中途看 live 分组"（本轮范围外）。

  • 同一份报告，skip_groups 里不存在同前缀同 kind 的两行，也不存在"某行是另一行前缀 + 同 kind"的情况。

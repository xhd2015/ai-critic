Services：手机端宽度修复 · Add/Edit 改为 Modal · 两个新环境选项

同一个页面上的三个问题一起看：① 390px 下卡片底部 8 个按钮把页面撑出横向滚动； ② 点 Edit / Add Service 时表单在列表下方原地展开、没有遮罩也没有滚动定位，看起来“悄无声息地打开在别处”； ③ 自定义服务还缺 “额外 PATH” 与 “继承 Interactive Shell 环境变量” 两个能力。

Mockup 假设（示意，不是真实数据）：服务名 web，npm run dev，端口 3000，状态 Running。 手机视口按 390×800 画；真实 CSS 断点复用了仓库里已有的 @media (max-width:720px)。 Modal 复用现成的 mcc-modal-overlay/mcc-modal 结构（KillProcessModal.css），手机端为底部抽屉、桌面端为居中对话框。 新字段的解析链路按 dot-pkgs 现成实现（shell/lookpath.ResolveLoginEnvs + MergeEnvs，bash -lic 'env -0'）推导，行为细节见下面“环境合并顺序”。

环境合并顺序（新选项在服务启动时的作用点）

1服务进程自身 envtool_resolve.AppendExtraPaths(os.Environ())
2＋ interactive shell env（勾选时）lookpath.ResolveLoginEnvs() → MergeEnvs(process, shell)
3＋ Extra PATHprepend dirs, de-dup, later dedupe against existing
4＋ Extra Envmap merge, last wins（含空值）
5＋ 只补缺失 CLIlookpath.LookupPaths(["go","node","npm"])
6启动前显式 export PATHbash -lc 'export PATH=…; <command>'

字段落点（前端）

  • ServiceFormState.extraPath: string、inheritShellEnv: boolean
  • 表单：Environment 分组，位于 Working Dir 之后、Extra Env 之前
  • 提交：saveService({ extraPath, inheritInteractiveShellEnv })
  • 回填：toFormState() 从 ServiceStatus 读同名字段
  • 卡片：Effective PATH 下方显示 ＋PATH n dirs / shell env 两个 chip

字段落点（服务端）

  • ServiceDefinition.ExtraPath string（JSON extraPath）
  • ServiceDefinition.InheritInteractiveShellEnv bool
  • buildServiceEnv() 按上面 6 步组装；解析失败降级为“忽略并继续”，不阻止启动
  • ServiceStatus 回传两个字段，保证表单 round-trip 不丢
  • CLI service add/update 是否补 --extra-path / --inherit-shell-env：待定
